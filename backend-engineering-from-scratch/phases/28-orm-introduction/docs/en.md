# Lesson 28: ORM Introduction

> **Motto**: An ORM maps relational database tables to object-oriented domain models, but it does not eliminate the need to understand SQL.

---

## Motto
"An ORM maps relational database tables to object-oriented domain models, but it does not eliminate the need to understand SQL."

## Problem
Developers who rely blindly on ORMs write catastrophic queries that fetch entire databases into memory.

## Prediction
Introducing an ORM only after mastering raw SQL reveals exactly what queries the abstraction generates.

## Why this matters
ORMs provide productivity for CRUD, migrations, and type safety, but debugging performance requires inspecting raw SQL.

## First principles
Object-Relational Mapping translates object graph traversals into relational SQL joins and selects.

## Debug it
Isolate the failing layer without guessing:
- **Diagnostic Method**: Inspect terminal logs; observe the unexpected hidden SQL SELECT query generated by the ORM attribute access.
- Trace request correlation IDs across application logs and exception stack traces

## Improve it
Apply defensive engineering to eliminate the vulnerability or bottleneck:
- **Defensive Refactoring**: Configure explicit eager loading (`joinedload` / `selectinload`) to eliminate accidental lazy queries.
- Enforce strict bounds, transactions, and fallback behaviors

## Security
Analyze the security boundary for this layer:
- **Threat Model**: ORM abstraction leaks: complex business calculations inside Python loops instead of SQL aggregates waste CPU and memory.
- Ensure principle of least privilege, input sanitization, and defense-in-depth

## Production implications
How this manifests in production infrastructure:
- **Production Operations**: Always verify generated SQL during code reviews; never merge ORM code without inspecting the query execution plan.
- Monitor RED telemetry signals and configure alert thresholds for SLO compliance
