# Complete JVM Internals Guide

A deep reference guide covering the architecture, memory areas, class lifecycle, JIT compilation, and garbage collection mechanisms of the HotSpot Java Virtual Machine.

---

## 1. Class Loading and Linking Lifecycle

The JVM does not load all classes at startup. Classes are discovered, validated, and initialized **lazily** upon first active use.

```text
 ┌──────────────┐
 │   Loading    │  Locate .class binary stream via ClassLoader hierarchy.
 └──────┬───────┘  Construct java.lang.Class instance in Metaspace.
        │
        ▼
 ┌──────────────┐
 │   Linking    │
 │              │
 │ ├─ Verify    │  Structural and type-safety check. Enforce operand stack depth,
 │ │            │  valid branch targets, no uninitialized variable reads.
 │ ├─ Prepare   │  Allocate static field storage in Metaspace and initialize to zero/null.
 │ └─ Resolve   │  Transform symbolic constant pool references into direct memory pointers.
 └──────┬───────┘
        │
        ▼
 ┌──────────────┐
 │Initialization│  Execute <clinit> method: run static initializers and static
 └──────────────┘  field assignment expressions in strict textual order.
```

### Active Triggers for Class Initialization:
* Executing `new` on the class.
* Reading or writing a static field declared by the class (excluding compile-time constants `static final primitive/String`).
* Invoking a static method declared by the class.
* Reflective invocation via `Class.forName()` (unless initialized=false).
* Being the initial main class passed to `java`.

## 2. HotSpot Object Memory Layout

Every Java object allocated on the heap conforms to an aligned byte structure:

```text
+-------------------------------------------------------------------+
|                        JAVA HEAP OBJECT LAYOUT                    |
+-------------------------------------------------------------------+
| 1. Mark Word (64 bits / 8 bytes)                                  |
|    - Identity hash code (31 bits)                                 |
|    - GC age bits (4 bits: max tenure age 15)                      |
|    - Biased lock / lock state bits (2 bits)                       |
|    - Thin lock monitor pointer or fat lock object monitor pointer |
+-------------------------------------------------------------------+
| 2. Klass Word (32 bits / 4 bytes with CompressedClassPointers)    |
|    - Native pointer to class metadata in Metaspace                |
+-------------------------------------------------------------------+
| 3. Instance Fields (variable size)                                |
|    - Primitive values (boolean/byte: 1B, short/char: 2B,          |
|      int/float: 4B, long/double: 8B)                              |
|    - Reference pointers (4B with CompressedOops, else 8B)         |
+-------------------------------------------------------------------+
| 4. Alignment Padding (0 to 7 bytes)                               |
|    - HotSpot enforces 8-byte boundary alignment                   |
+-------------------------------------------------------------------+
```

### Example: Object Size Calculation
Consider an instance of:
```java
public class User {
    private long id;        // 8 bytes
    private int age;        // 4 bytes
    private boolean active; // 1 byte
    private String name;    // 4 bytes (compressed reference)
}
```
* **Mark Word**: 8 bytes
* **Klass Pointer**: 4 bytes
* **Fields**: $8 + 4 + 1 + 4 = 17$ bytes
* **Subtotal**: $8 + 4 + 17 = 29$ bytes
* **Padding**: 3 bytes (to reach next multiple of 8: 32 bytes)
* **Total Shallow Heap Size**: **32 bytes**.

## 3. Tiered Compilation and the JIT Engine

HotSpot utilizes a 5-tier dynamic compilation system:

```text
[Bytecode] ──► Level 0: Interpreter
                  │
                  ▼ (Invocation / Backedge counter threshold reached)
              Level 1: C1 Compiler (Simple native code, no profiling)
                  │
                  ▼
              Level 2: C1 Compiler (Basic profiling)
                  │
                  ▼
              Level 3: C1 Compiler (Full profiling: branch frequencies, receiver types)
                  │
                  ▼ (Method deemed "Hot")
              Level 4: C2 Compiler (Deep optimization: Escape Analysis, Inlining, Loop Unrolling)
```

### JIT Deoptimization ("Deopt")
C2 compiler optimizations are **speculative**. For example, C2 might inline a method because profiling shows 100% of calls targeted `Dog.speak()`. If the application later passes a `Cat`, the assumption is violated:
1. The CPU hits an "uncommon trap" generated by C2.
2. The executing native stack frame is transformed back into an interpreted bytecode stack frame on the fly.
3. Execution safely resumes in the interpreter.

## 4. Modern Garbage Collection Comparison

| Collector | Target | Algorithm | Pause Latency | Max Recommended Heap |
| :--- | :--- | :--- | :--- | :--- |
| **Serial GC** (`-XX:+UseSerialGC`) | Single-threaded CLI/embedded | Mark-Copy Young, Mark-Sweep-Compact Old | High (Full STW) | < 100 MB |
| **Parallel GC** (`-XX:+UseParallelGC`)| Batch processing, max throughput | Multi-threaded STW Young & Old | High throughput, seconds pause | Unlimited |
| **G1 GC** (`-XX:+UseG1GC`) | Default server workloads | Region-based, generational, concurrent marking | Predictable (default 200ms target) | 4 GB - 64 GB |
| **Generational ZGC** (`-XX:+UseZGC`) | Ultra-low latency, mission critical | Concurrent colored pointers & load barriers | Sub-millisecond (< 1ms) | Up to 16 TB |

## 5. Critical HotSpot Diagnostics Flags

```bash
# Print all default and active JVM flags
java -XX:+PrintFlagsFinal -version

# Enable GC logging with unified logging framework
java -Xlog:gc*,gc+phases=debug:file=gc.log:time,uptime,pid:filecount=5,filesize=100M -jar app.jar

# Dump heap automatically on OutOfMemoryError
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps/oom.hprof -jar app.jar

# Disable compressed pointers for debugging 64-bit reference expansion
java -XX:-UseCompressedOops -XX:-UseCompressedClassPointers -jar app.jar

# Force C2 compiler compilation logging
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation -jar app.jar
```
